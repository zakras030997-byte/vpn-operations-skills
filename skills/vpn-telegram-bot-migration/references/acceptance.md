# Приёмка переноса или восстановления бота

Для каждого затронутого критерия укажи версию/digest, среду, свидетельство и `passed`/`failed`/`blocked`/`not tested`. Выбирай проверки по изменению; не запускай заново общий аудит при наличии пригодных результатов. Количество тестов не является критерием полноты приёмки.

## До остановки действующего бота

Применяй только к затронутым компонентам; используй уже проверенные свидетельства той же версии. Не создавай второй общий аудит.

- На целевой архитектуре проверь фактические команды запуска и import-порядок, обязательные assets, UID/GID, доступ к нужным путям/volumes и конфигурацию зависимостей. Синтетическая проверка использует тот же образ и команды, но отключённые внешние эффекты; она не разрешает standby с рабочим polling/writers.
- Укажи, что проверено изолированно, а что требует защищённого рабочего контура. Доступы и секреты не подменяй результатами fake-клиента. Для оставшегося пункта подготовь точную проверку и условие возврата; отсутствие обязательной предпосылки блокирует остановку.
- Зафиксируй согласованные критерии успеха, допустимый срок переключения, команду/версию совместимого адресного возврата и необходимые сведения о текущих данных. Правила копии, единственного consumer и сохранности данных — в разделах «Переключение» этого скилла и «Установка» ниже.

## Изолированная проверка фактического кандидата

| Путь | Наблюдаемое требование |
| --- | --- |
| `/start` и информационные кнопки | Настоящие dispatcher/router/middleware вызывают ожидаемые методы Telegram; unexpected provider/financial call отвергается fake-сервисом |
| ACK | Разрешённая доказанная причина обрабатывается узко; другой метод/ID/причина не подавляются |
| Edit и send | Доказанный отказ редактирования даёт одну отправку подготовленного экрана; отказ отправки не становится успешной доставкой |
| Pending/unknown | Pending и исходный unknown сохраняются; следующий update не теряется; финансовый unknown не повторяется |
| Операторское решение, если добавлено | Только exact событие допускает продолжение, original не меняется, handler не повторяется; несовпадения блокируют |
| ACL и FSM | Посторонний пользователь не получает admin view; нужные формы переживают restart, штатные переходы состояния согласованы |
| SQLite, если изменено | При удержании lock heartbeat работает, commit корректен после освобождения; backoff имеет предел, без потери события и дубля |
| Restart и повтор, если путь затронут | Persisted pending сохраняется; подтверждённая операция не выполняется дважды; неопределённый исход не повторяется автоматически |
| Платежи/выдача, если путь затронут | Синтетический повтор callback/запроса и сбой между commit и ответом не создают второй платёж, выдачу или outbox-эффект |
| Недоступность прежнего узла, если связь остаётся | Изолированный отказ API/bridge не даёт ложной готовности и не теряет состояние; поведение соответствует проверенному контракту |

Рабочий токен, production БД/секреты и внешний провайдер не использовать. Изоляция действует до app imports и включает побочные фоновые задачи. Фиксируй реальные ограничения sandbox/контейнера; monkeypatch не называй OS isolation. Проверяй что код не подменён reference-моделью. Stub бизнес-сервиса проверяет handler, а реальный путь DB/provider требует отдельного анализа/теста.

## Установка

- Установленные image digest, spec, manifest, исполняемые файлы и assets соответствуют проверенному кандидату. Старые mutable теги или другая копия модуля не являются доказательством.
- Ровно один владелец Telegram consumer и относящихся jobs; старый consumer остановлен/fenced вместе с автозапуском. Для webhook сверены фактический маршрут и отключение старого обработчика в согласованных границах.
- Действующий authority сохранён при bot-only ремонте. Смена generation не возникает из исправления отображения.
- Актуальный backup проверен; addressed rollback сохраняет новые операции и совместим с текущей схемой. Не обещай работоспособность известного дефектного старого образа.

## Реальные функции после установки

1. Свежий `/start` имеет время после переключения; новая панель действительно появилась. Старый queued `/start` не заменяет этот критерий.
2. Открываются основные информационные кнопки владельца, соответствующие текущему продукту. Например: состояние, заявки, действующие ключи и список клиентов — если такие функции есть в продукте. Платёж/выдачу не запускать случайным нажатием.
3. Новые события имеют корректный итог; фактическая отправка/редактирование приняты Telegram. `done` пригоден как доказательство только после проверки семантики кода; иначе покажи отдельную квитанцию ответа. Экран клиента и принятие API различай явно.
4. Нет новых необъяснённых unknown/processing, падений или рестартов в проверенном интервале. Длительность интервала укажи, не обещай устойчивость из одного запроса.
5. Сверка актуального before/current по стабильным ID показывает сохранность прежних данных и допустимые новые операции. Одни counts недостаточны: проверяй относящиеся поля/строки или hashes. Штатный рост ledger/FSM после реальных действий отличай от потери/сброса.
6. Соседние службы проверены в пределах затронутых зависимостей; неизменённый PID подтверждает отсутствие restart, а не все функции службы.

При отсутствии разрешённого клиента/действия владельца серверная часть может быть проверена, пользовательская приёмка остаётся `blocked`/`not tested`. Дай один шаг владельцу и дождись ответа. Ошибки live-метрик, VPN/HAPP, платежей и выдачи перечисли отдельно, не выдавай исправность меню за их приёмку.

# Единый отчёт VPN · v1.1

Все администраторы используют одинаковый порядок разделов. Не заменяй абсолютные значения одними процентами. Неизвестное обозначай «не проверено: причина», отсутствие — только после проверки. Значения ниже — поля шаблона, не результаты измерений.

## 1. Узел и итог

Узел / hostname; дата, время и часовой пояс; run-id / assignment-id; версия формата 1.1; статус OK / WARN / CRITICAL / UNKNOWN; краткий вывод; полнота проверки; uptime; сравнение с предыдущим снимком или «первый снимок».

## 2. Ресурсы

| Показатель | Занято / всего | Свободно / доступно | Нагрузка и состояние |
|---|---|---|---|
| Диск, точка монтирования | … GiB / … GiB (…%) | … GiB (…%) | норма / внимание |
| RAM | … GiB / … GiB (…%) | MemAvailable … GiB (…%) | норма / внимание |
| Swap | … GiB / … GiB | … GiB | либо отсутствует |
| CPU | … vCPU | — | загрузка: минимум / среднее / максимум …% за … замеров |
| Load average | — | — | 1 / 5 / 15 минут: … / … / …; при … vCPU |
| Inode, точка монтирования | … / … (…%) | … (…%) | норма / внимание |

GiB = 1024³ байт, одинаково для всех узлов. RAM «занято» = MemTotal − MemAvailable; это оценка памяти, недоступной для новых задач, а не сумма RSS процессов. Кеш не объявляй дефицитом. Для диска показывай фактическое used и size файловой системы; available может не дополнять used до size из-за резерва. Показывай корневую и отдельные файловые системы данных/backup; одну FS не суммируй несколько раз через bind/overlay mounts. Диск и RAM не выводи из округлённых процентов. При недостатке исходных чисел запроси узкий дозамер. Без swap пиши «отсутствует», не дели на ноль. CPU — загрузка хоста 0–100%; контейнерные CPU% могут превышать 100%, не смешивай их с хостом.

## 3. VPN-протоколы и зависимости

| Протокол / компонент | Служба или контейнер | Состояние процесса | Порт / транспорт | Прикладная проверка | Итог |
|---|---|---|---|---|---|
| Фактически настроенный протокол | точное имя | running / stopped / unknown | … TCP/UDP | трафик подтверждён / только порт / не проверено | OK/WARN/CRITICAL/UNKNOWN |

Перечисли все настроенные протоколы (например VLESS, Trojan, Hysteria2, AmneziaWG — только если реально есть), а отдельно — API, бот, учёт трафика и межсерверный туннель. Процесс active и открытый порт не доказывают прохождение VPN-трафика. Не раскрывай ключи, UUID пользователей или ссылки подписок.

## 4. Контейнеры и основные службы

Контейнерный движок: Docker / Podman / отсутствует / недоступен.
Всего контейнеров: …; running: …; exited: …; restarting: …; paused: …; created/dead/removing: … . Сумма состояний должна равняться общему числу. Отдельно: unhealthy …; healthcheck отсутствует …; требуют внимания … (эти признаки пересекаются с состояниями и не прибавляются к общему числу). При нескольких движках — отдельные итоги и общий итог без двойного счёта; при ограниченных правах укажи область видимости, не утверждай полный итог сервера.

| Основной контейнер | Роль | State / health | CPU / RAM | Рестарты всего / новые | Требует внимания и почему |
|---|---|---|---|---|---|
| точное имя | VPN/API/БД/бот/monitoring | … / нет healthcheck | …% / … MiB; лимит если задан | … / … либо сравнение недоступно | … |

Перечисли все основные контейнеры и каждый проблемный, даже неосновной. Штатную завершённую одноразовую задачу не называй аварией. Отсутствие healthcheck не равно unhealthy. Новые рестарты вычисляй только для того же ID; новый ID сверяй с deploy. Если контейнеров нет, пиши «0; VPN работает через systemd» только после проверки и перечисли основные systemd-службы с состоянием и новыми рестартами. Ошибка доступа не означает отсутствие движка/контейнеров.

## 5. Ошибки и безопасность за 24 часа

Новые падения, OOM, рестарты, ошибки приложений/учёта, сетевые аномалии; время и безопасное свидетельство; установленная причина или гипотеза; влияние. Для количества ошибок укажи диапазон и полноту выборки. Число записей ошибок не выдавай за процент неуспешных операций. Исторические счётчики отделяй от событий последних суток.

## 6. Сертификаты и резервирование

Сертификат: назначение, срок окончания с часовым поясом, дней осталось, статус. Backup: что резервируется, безопасное место хранения без credentials, дата последней подтверждённой копии, возраст, результат задания и дата последней проверки восстановления либо «не проверено». Наличие старого архива не доказывает регулярное резервирование.

## 7. Действия и решения

Исправлено: объект, действие, проверка после и откат; либо «не выполнялось».
Осталось: проблема → следующий конкретный шаг → ответственный → приоритет.
Решение владельца: не требуется / требуется <точное решение, влияние, риск, откат>.
Непроверено: перечень и причины. Материалы: безопасный путь к снимку/исследованию.

Координатор сохраняет отчёты в этом формате. Для общей сводки использует таблицу «узел | статус | диск занято/всего | RAM занято/всего | CPU | контейнеры running/всего, внимание | протоколы и степень проверки | ключевая проблема | нужно решение». Срочное уведомление может быть коротким и предварительным; полный ежедневный отчёт дополняется по готовности, без задержки критической эскалации.

## Качество ежедневной отчётности

Цель: из отчёта понятно, что работает, что ухудшилось, влияние на пользователей и ответственный. Сохраняй формат v1.1 и границы исправлений.

1. Начинай с общего статуса, главной проблемы или отсутствия существенных проблем, влияния (подтверждено / возможно / не проверено) и необходимости решения владельца.
2. Ресурсы показывай одинаково: диск/RAM/swap занято/всего, процент и остаток; CPU vCPU, среднее и максимум за указанный период; load за 1/5/15 минут. Добавляй изменения к предыдущему снимку в абсолютных единицах и процентных пунктах, либо объясняй невозможность сравнения.
3. Для каждого протокола отдельно укажи службу, ожидаемый порт, разрешённую прикладную проверку и подтверждение реального трафика. Запущенный процесс не доказывает исправность протокола.
4. Показывай общее число контейнеров и распределение состояний, основные и все проблемные: имя, роль, state/health, CPU/RAM, новые рестарты, причина внимания. Без контейнеров перечисляй основные systemd-службы. Штатные завершённые задачи отделяй от аварий.
5. Для нерешённой проблемы веди одну карточку: incident-id, узел, первое обнаружение, последнее наблюдение, симптом, доказательства, влияние, причина или гипотеза, приоритет, ответственный, следующий шаг, срок следующей проверки, решение владельца. Повтор того же симптома обновляет карточку, не создаёт новую.
6. Различай: обнаружена; исправление выполнено и проверено; устранение подтверждено последующим наблюдением. Один успешный API-запрос после периодических ошибок не доказывает устойчивого устранения. Последующее наблюдение — следующий плановый цикл или отдельно разрешённая проверка, без расширения мониторинга.
7. Сопоставляй времена и зависимости узлов. Ошибки нескольких узлов могут иметь общую API-зависимость, но общую причину утверждай только после подтверждения. Одно согласованное расследование, без параллельных изменений зависимости.
8. Принимай отчёт после проверки абсолютных ресурсов и времени, согласованности контейнерных итогов, отделения исторических рестартов от новых. Число error-записей не равно доле отказов; старый архив не равно актуальный backup. Непроверенное явно обозначено. Запрашивай только недостающие сведения, без полного повторного скана.
9. Владельцу — компактная сводка узлов и необходимые решения; подробные свидетельства — в материалах. Срочный инцидент сообщай сразу, не ожидая заполнения полей.
10. Уведомления выполняй по действующей согласованной политике; необходимое решение сопровождай конкретным предложением, риском и откатом. Сам отчёт не разрешает email. Полномочия на изменения серверов не расширяются.

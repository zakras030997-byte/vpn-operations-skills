# Приёмка многоэтапных VPN-работ

## Договор о результате

Для каждого этапа закрепи assignment-id, содержательную версию, утверждённую цель, разрешённые действия, обязательные результаты и одного ответственного за интеграцию. Раздели независимые работы и зависимости. Не запускай зависимый прогон на незавершённой поставке; подготовка runner может идти независимо. Уточнение внутри этапа использует тот же assignment-id, а новая содержательная поставка получает новую версию.

## Проверяемая поставка

Когда один исполнитель передаёт код другому для интеграции, согласуй формат пакета до завершения разработки. Минимум: candidate-id/версия, точный путь, список файлов и SHA256, версии зависимостей/lock, требуемая схема и миграции, команды воспроизведения, условия изоляции и безопасные тестовые входы. Хеши фиксируются после правок; каждое последующее изменение создаёт новую версию. Получатель сверяет хеши до запуска и после копирования в изолированную рабочую папку. Изменяемая рабочая папка не является зафиксированной поставкой.

Не включай production DB, токены, секретные env, клиентские данные, caches или runtime-состояние в синтетический пакет. Не назначай экспорт образов/секретов из полномочий на локальную разработку. Если проверяются несколько служб, фиксируй образ/код/entrypoint/schema каждой: успешный тест одного бота не доказывает совместимость всего комплекта.

## Матрица приёмки

Веди одну матрицу в материалах этапа:

| Критерий ТЗ | Ответственный | Версия/материал | Проверка и уровень | Результат | Пробел/следующее действие |
|---|---|---|---|---|---|

Результаты: подтверждено / частично / не проверено / блокировано / не применимо с причиной. Указывай время изменяющихся наблюдений. Заявление исполнителя отделяй от прочитанного журнала и независимо воспроизведённой проверки. Матрица не заменяет содержательную оперативную карточку.

Различай уровни доказательства:
- Модель/заглушка: проверяет предложенную семантику, не deployed реализацию.
- Настоящий код с synthetic DB: проверяет зафиксированную ревизию и выбранные сценарии.
- Интеграция комплекта: actual entrypoints, schema/startup, взаимодействие служб и владельцы jobs/consumer, включая отказные сценарии.
- Целевой runtime: запуск и ограничения именно на целевой площадке в разрешённой изоляции.
- Production/клиент: отдельно разрешённые реальные функции и пользовательская приёмка.

Чистый validator, HTTP200, mock command executor, audit guard и декларация CPU/PID/disk limits подтверждают только свои границы. Audit guard не объявляй OS sandbox; fake Xray/tc не доказывают host execution. Не требуй production проверки для этапа, который утверждён только как локальная подготовка, но сохраняй эту границу в итоговом статусе.

## Зависимые назначения

По готовой поставке координатор проверяет обязательные материалы, сохраняет решение в существующей оперативной карточке и назначает получателю конкретный прогон с версией/путём/критериями. Если пакет отсутствует, передай поставщику точные недостающие входы; не повторяй всю разведку и не проси получателя запускать mutable код. Неполный результат не закрывай пересмотром требований без решения владельца.

После передачи один раз проверь доставку и заверши ход. Ожидание зависимости не является сбоем; не создавай polling/мониторинг без отдельного поручения. При входящем результате продолжай разрешённую цепочку по подтверждённым входам.

## Продолжение после сжатия истории

До длинной работы сохрани в материалах компактную точку продолжения: assignment-id/версию, текущую цель и этап, прямое основание разрешений, границы, владельцев изменений, пути к текущим поставкам, принятые критерии, пробелы и следующий конкретный шаг. Секреты и сырые переписки не сохраняй.

После восстановления сначала прочитай эту точку и актуальное поручение. Не подменяй разработку общим сканом, контракт — аудитом, интеграцию — новым модельным стендом. Если версия изменилась, сначала сверяй её; не запускай дубликат назначения. При утрате существенного входа обозначь конкретный пробел и продолжай независимую часть.

## Закрытие этапа

Этап завершён только когда все обязательные критерии подтверждены на требуемом уровне, материалы доступны и ограничения отражены. Число passed tests не является отдельным критерием полноты. Подзадача может завершиться при незавершённом этапе; используй разные статусы.

При пробелах назначь только недостающую работу в разрешённом объёме. Решения о production fail policy, новых расходах, данных и переключении не принимай из тестового default. Невозможность продолжить фиксируй с доказательством и необходимым решением, без ложного «готово».

Итог: версия, закрытые критерии, доказательства, ограничения и следующий шаг либо остановка по поручению владельца. Обнови одну связанную оперативную карточку и перечитай запись. Email/PNG/следующий этап выполняй только по действующему поручению; изменение скилла само по себе этот цикл не запускает.

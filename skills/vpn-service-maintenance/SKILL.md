# Обслуживание VPN и центрального управления

Работай только с назначенными узлами и в согласованном объёме. Скилл не предоставляет доступ и не разрешает production-изменения сам по себе. Начни с чтения точного объекта, зависимостей и актуального состояния.

При обычном обслуживании сохраняй действующие URL подписок, credentials, идентификаторы, сроки, квоты, платежи и накопленный трафик. Отключение одного протокола не разрешает изменение других регионов, firewall или общих API. Не восстанавливай старую БД поверх новых операций. Не меняй единственный рабочий путь VPN-доступа без проверенного независимого доступа и адресного возврата.

Для учёта каждого источника сохраняй cumulative checkpoint и идентификатор процесса/epoch. Повторный снимок не начисляет трафик дважды; счётчик не сбрасывается при опросе. Не определяй совместимость копируемых контейнеров только по именам: проверь общие volumes, writers, API, jobs и checkpoints.

При переносе центральной группы используй [references/control-plane-migration.md](references/control-plane-migration.md). Для Telegram-части используй [vpn-telegram-bot-migration](../vpn-telegram-bot-migration/SKILL.md). Перенос центра не переносит региональный VPN-трафик автоматически.

Перед разрешённым изменением подготовь актуальную защищённую копию, проверку пригодности восстановления, точную версию и совместимый откат. Меняй минимально необходимый объект. При неизвестном исходе операции сначала проверь состояние; не повторяй внешний эффект вслепую.

После изменения отдельно проверяй серверную функцию, прежнюю подписку и реальное клиентское подключение. Running, порт или HTTP 200 доказывают лишь проверенный слой. Отчёт содержит версию, изменение, свидетельства, сохранность данных, откат и непроверенные условия. Email, мониторинг и дополнительные изменения требуют действующего поручения.
